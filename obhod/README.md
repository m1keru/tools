# obhod

Доступ в интернет в обход российских блокировок, который не держится на одном
протоколе и одном сервере. Утилита хранит ключи, собирает установщики серверов
и клиентские конфиги и умеет определить, под каким видом блокировки оказался
узел.

Состояние на ноябрь 2026. Правила фильтрации меняются еженедельно, поэтому
раздел [«Что проверено»](#что-проверено-и-что-нет) стоит прочитать до
первого запуска.

## Модель угрозы

ТСПУ блокирует в первую очередь по адресу и поведению, а не по сигнатуре
протокола.

| Механизм | Что происходит | Что из этого следует |
|---|---|---|
| Репутация IP и ASN | TLS-соединение к зарубежному дата-центру замирает после ~16–20 КБ (≈25 пакетов), без разрыва. С августа 2026 блокируют ASN целиком. | Решает выбор хостера, а не протокола. |
| Правило всплеска | Больше 3 TLS-рукопожатий к одному имени за 60 с дают заморозку на ~120 с. | Клиент обязан жить на 1–2 долгих соединениях. |
| Отпечаток TLS | Целились в uTLS-профиль Chrome 133; смена отпечатка во время заморозки продлевает её до ~600 с. | Отпечаток задаётся в одном месте и меняется осознанно. |
| Сигнатуры | WireGuard, OpenVPN, IKEv2, Shadowsocks, SOCKS5, MTProto не работают. VLESS+TCP+REALITY ловят волнами с февраля 2026. | Основной транспорт: XHTTP. |
| Активное зондирование | Узел без правдоподобного сайта за ним попадает в список. | REALITY отдаёт зонду настоящий чужой сайт. |
| UDP | На части операторов один UDP-пакет к наблюдаемому адресу блокирует адрес на минуты. | UDP-транспорт никогда не проверяется автоматически. |
| Белые списки (мобильные сети) | Пропускаются только разрешённые SNI и подсети. | Нужна точка входа на российском адресе; протокол не поможет. |

Пороги взяты из общественных отчётов, а не из измерений этой утилиты; список
источников в конце.

## Почему не свой протокол

Когда замораживают любой TLS-поток к «подозрительному» адресу, новизна
протокола ничего не даёт, а непроверенная криптография добавляет риск.
Устойчивость дают четыре вещи, и утилита автоматизирует именно их:

1. **Несколько транспортов с несвязанными причинами отказа** на каждом узле.
2. **Несколько узлов** в разных странах и ASN.
3. **Дисциплина клиента**: мало рукопожатий, никаких фоновых проверок, которые
   сами вызывают блокировку.
4. **Диагностика и быстрая ротация**: понять, что именно сломалось, и заменить
   узел одной командой.

## Архитектура

```
                      ┌─ xhttp   TCP/443   VLESS + XHTTP + REALITY + Vision   основной
клиент ──────────────►├─ vision  TCP/8443  VLESS + REALITY + Vision           быстрый
   │                  └─ hy2     UDP/443   Hysteria2 + Salamander             запасной
   │                       выходной узел nl1, второй такой же узел fi1
   │
   └──► relay ru1 (российский адрес) ──xhttp──► nl1        для белых списков
```

Все три транспорта обслуживает один процесс Xray. Российские адреса клиент
отправляет напрямую, узлы их не принимают вовсе: адрес узла не появляется в
логах российских сервисов. Исходящий TCP/25 закрыт на всех
узлах: заражённое устройство не сможет рассылать через узел спам и занести
его адрес в почтовые чёрные списки.

| Профиль | Когда использовать |
|---|---|
| `*-xhttp` | По умолчанию. Два долгоживущих соединения, не задевает правило всплеска. |
| `*-vision` | Домашний провайдер, где правило всплеска не действует: заметно быстрее. |
| `*-hy2` | Сеть с потерями или когда TCP к узлу заморожен. Включать вручную. |
| `ru1-*` | Сеть пускает только на российские адреса. |

## Быстрый старт

Нужны Go 1.22+ на своей машине и два VPS с Debian или Ubuntu.

```sh
cd obhod && go build -o obhod .

./obhod init
./obhod node add -name nl1 -addr 203.0.113.10 -target www.example.org:443
./obhod node add -name fi1 -addr 198.51.100.7 -target cdn.example.net:443
./obhod render

ssh root@203.0.113.10 'bash -s' < out/nodes/nl1/install.sh
ssh root@198.51.100.7 'bash -s' < out/nodes/fi1/install.sh

./obhod probe          # из своей сети, с выключенным VPN
```

`obhod.json` и каталог `out/` содержат приватные ключи. Оба в `.gitignore`;
держите резервную копию `obhod.json` вне сервера.

### Установщик

По умолчанию `install.sh` трогает только `/opt/obhod`, один unit systemd (на
хосте без systemd это init-скрипт `/etc/init.d/obhod-xray`) и одного
системного пользователя, поэтому его можно запускать на сервере, который занят
другой работой. Всё более широкое включается явно.

| Вызов | Что делает |
|---|---|
| `bash -s -- --check` | Проверяет хост и ничего не меняет: ядро, систему инициализации, свободные порты, место, инструменты. |
| `bash -s` | Ставит или обновляет узел. |
| `--open-firewall` | Открывает порты узла в уже включённом ufw или firewalld. |
| `--tune-network` | BBR и увеличенные буферы. Только для выделенного VPS: меняет сетевые настройки всего хоста. |
| `--install-deps` | Ставит недостающие `curl` и `unzip` пакетным менеджером. |
| `--xray-zip ПУТЬ` | Берёт архив Xray с диска сервера: для хостов, чей `curl` не может скачать его с GitHub. |
| `--uninstall` | Удаляет узел. |

Для свежего выделенного VPS: `bash -s -- --open-firewall --tune-network`.

Перед установкой на сервер, где уже что-то работает, посмотрите на него
скриптом, который только читает состояние:

```sh
ssh ПОЛЬЗОВАТЕЛЬ@СЕРВЕР 'bash -s' < scripts/recon.sh
```

Он покажет, запустится ли Xray на этом ядре, какие порты заняты и чем, и
дотягивается ли хост до GitHub. Если 443 занят, задайте узлу другие порты:
`obhod node add ... -xhttp-port 8443 -vision-port 9443 -hy2-port 0`. На
старых системах (systemd младше 229 или ядро младше 4.3) узлу доступны только
порты выше 1024.

Systemd не обязателен. На старых Debian с sysvinit узел ставится init-скриптом
на `start-stop-daemon` и включается в автозагрузку через `update-rc.d`. Порты
там тоже только выше 1024, упавший Xray никто не перезапускает, а журнал
`/opt/obhod/log/xray.log` не ротируется.

Клиентам:

- **Телефон.** Импортируйте `out/clients/me/links.txt` (или `sub.txt` как
  подписку) в приложение на ядре Xray. Профилям `xhttp` нужно свежее ядро
  с VLESS Encryption: по отчёту от 25.10.2026 это Xray 26.9 и новее
  (например, Happ). sing-box, насколько известно, XHTTP не поддерживает:
  таким клиентам доступны только `vision` и `hy2`.
- **Компьютер.** `xray run -c out/clients/me/xray/auto.json` поднимает на
  `127.0.0.1` SOCKS5 и HTTP-прокси с паролем. Адреса, порты и пароль записаны
  в `out/clients/me/proxy.txt`; у каждого пользователя они свои и между
  запусками `render` не меняются. `auto.json` переключается между
  XHTTP-профилями сам; файлы `<узел>-<транспорт>.json` закрепляют один
  профиль.

## Выбор хостера и сайта-цели

От этих двух решений зависит больше, чем от всего остального.

**Хостер.** Два узла в разных странах и разных ASN, у небольших провайдеров.
Крупные (в отчётах называют Hetzner, DigitalOcean, OVH) чаще других попадают
под заморозку по объёму. Сразу после установки запустите `obhod probe`:
вердикт `VOLUME_FREEZE` означает, что адрес уже в списке и узел надо
переносить, пока действует возврат денег.

**Сайт-цель REALITY** (`-target`). Зонд цензора, пришедший на ваш адрес,
увидит этот сайт, поэтому он должен быть правдоподобным соседом сервера:

- размещён в той же ASN, что и сервер (ищется утилитой RealiTLScanner,
  запущенной на самом сервере);
- отвечает по TLS 1.3 и HTTP/2, без редиректа на другой домен:
  `curl -sI --tlsv1.3 --http2 https://ИМЯ`;
- в имени нет `vpn`, `proxy`, `node` и подобного; это не google, microsoft или
  apple: ваш адрес не в их сетях. `obhod` предупредит о таких именах.

Команду `curl` запускайте там, где он умеет TLS 1.3: штатный curl macOS и
старых дистрибутивов не умеет. Xray при запуске пишет предупреждение
(`Choosing "…" as the target…`) на любое имя в зонах `.ru`, `.ir` и `.cn`.
У входа внутри России оно появится всегда: сосед по ASN там российский.

## Правила на клиенте

- **Отключите в приложении автотест и «пинг всех серверов».** Каждая проверка
  есть рукопожатие, пачка проверок сама вызывает правило всплеска.
- После зависания ждите 130 секунд, ничего не меняя. Не переключайте профили
  чаще и не меняйте отпечаток TLS в это время.
- Российские сайты направляйте мимо туннеля (в конфигах для компьютера это
  уже сделано; в мобильном приложении включите соответствующее правило
  маршрутизации).
- Отпечаток задаётся командой `obhod set -fp ...`, по умолчанию `firefox`.
  На ядре Xray v26.11.9 и новее годится и `chrome`: там он обновлён до
  Chrome 155.

## Программы на том же устройстве

Любая программа на устройстве может попытаться выяснить адреса узлов и
сообщить их своему серверу. Что от этого закрыто:

- **Локальный прокси.** Он требует пароль и слушает не на стандартном порту
  Xray. Не зная пароля, программа не может отправить через него запрос и
  узнать, с какого адреса выходит туннель.
- **Российские сервисы.** Запросы к ним идут мимо туннеля, а узлы российские
  адреса не принимают, поэтому адрес узла такой сервис не увидит. Прокси
  задавайте в настройках самого браузера (Firefox это умеет), а не в
  системных: тогда остальные программы в туннель не попадают вовсе.

Что не закрыто:

- сам факт работы туннеля: процесс, открытый порт и сетевой интерфейс видны
  любой программе;
- на компьютере программа, запущенная от того же пользователя, может прочитать
  конфиг клиента вместе с паролем прокси и таблицу соединений, то есть узнать
  адрес узла. От этого помогает только отдельное устройство или виртуальная
  машина;
- программа, которую вы сами пустили в туннель, узнаёт адрес выхода одним
  запросом к зарубежному сервису;
- в мобильных приложениях маршруты и локальный порт задаёт приложение, а не
  `obhod`.

## Диагностика

```sh
./obhod probe                 # все узлы
./obhod probe -burst nl1      # дополнительно проверить правило всплеска
./obhod probe -path /static/app.js nl1
```

Проба не говорит ни на одном туннельном протоколе. Обычный TLS-клиент, не
прошедший проверку REALITY, пересылается на сайт-цель, и ответ настоящего
сайта идёт тем же путём и с того же адреса, что и трафик туннеля. Этого
достаточно, чтобы различить виды блокировки.

| Вердикт | Что это | Что делать |
|---|---|---|
| `CLEAN` | TCP, TLS и объём проходят. | Если профиль всё равно не работает, цензор реагирует на поведение: сменить транспорт, обновить ядро в клиенте. |
| `IP_BLOCKED` | Пакеты к адресу пропадают. | Сменить IP (другая /24 или другой хостер). Пока работать через второй узел. |
| `VOLUME_FREEZE` | Соединение замирает после первых килобайт. | Свойство адреса и ASN: перенести узел или идти через relay. Hysteria2 на том же адресе может работать. |
| `TLS_BLOCKED` | TCP открывается, рукопожатие зависает. | Подождать 130 с и повторить. Если не прошло, сменить сайт-цель. |
| `BURST_RULE` | Сеть наказывает частые рукопожатия. | Только профили `xhttp`; `vision` в этой сети использовать нельзя. |
| `BAD_TARGET` | Узел отдаёт сертификат не для своего имени. | Сайт-цель выбран неверно: заменить. |
| `SERVICE_DOWN` | Порт закрыт, хост отвечает. | Это не блокировка: `systemctl status obhod-xray`, firewall хостера. |
| `INCONCLUSIVE` | Сайт-цель закрыл соединение раньше, чем набрался объём. | Повторить с `-path` на крупный файл сайта-цели. |

Ограничения пробы: она идёт с TLS-отпечатком Go, а не браузера, поэтому
блокировку по отпечатку не видит; Hysteria2 она не трогает, чтобы не
спровоцировать блокировку адреса; результат верен только для той сети, откуда
запущена.

## Эксплуатация

```sh
# Адрес узла заблокирован: новый IP, новые ключи.
./obhod node rotate -name nl1 -addr 203.0.113.99 -rekey

# Сайт-цель перестал подходить.
./obhod node rotate -name nl1 -target other.example.org:443

# Утёк клиентский конфиг или потерян телефон.
./obhod user rm anna            # и переустановить узлы

# Новый человек.
./obhod user add anna

# Новая версия Xray на серверах.
./obhod set -xray v26.11.9
```

После любой команды: `./obhod render` и повторный запуск `install.sh` на
затронутых узлах; утилита называет, на каких. Установщик сначала проверяет
новый конфиг командой `xray run -test` и не трогает работающий сервис, если
проверка не прошла. Если сервис с новым конфигом не поднялся, установщик сам
возвращает предыдущий из `/opt/obhod/etc/config.json.bak`. Удаление с сервера:
`ssh root@СЕРВЕР 'bash -s -- --uninstall' < install.sh`.

На сервере: сервис `obhod-xray`, файлы в `/opt/obhod`, журнал
`journalctl -u obhod-xray` (на sysvinit: `/etc/init.d/obhod-xray status` и
`/opt/obhod/log/xray.log`). Журнал обращений выключен: сервер не хранит, кто
куда ходил.

## Relay для белых списков

```sh
./obhod node add -name ru1 -addr РОССИЙСКИЙ_IP -target российский-сайт.example:443 \
    -upstream nl1 -hy2-port 0
./obhod render
# переустановить nl1 (на нём появилась учётная запись relay) и установить ru1
```

Relay принимает клиентов на российском адресе и отправляет трафик на выходной
узел по XHTTP. В `auto.json` relay стоит последним и включается, только когда
не отвечает ни один выходной узел.

Российские назначения relay по умолчанию не принимает, клиент отправляет их
напрямую. Иначе российский сервис видел бы адрес relay, тот самый, на который
подключаются клиенты. В сети с белыми списками прямые соединения с сайтами вне
списка не работают. Если они нужны, добавьте узел с флагом `-allow-ru`: такой
relay обслуживает российские назначения сам, а `ru1-xhttp.json` отправляет
через него весь трафик. Цена: его адрес появится в логах российских сервисов.

Это аварийный уровень, а не основной:

- работает, только если адрес relay попал в белый список оператора, а такие
  адреса дефицитны и список меняется (по сообщениям, 24 января 2026 часть
  подобных схем перестала работать);
- российский хостер знает владельца сервера и обязан выдавать данные по
  запросу;
- при полном отключении мобильного интернета не поможет ничего.

## Что вне этой утилиты

- **Без сервера.** Для ресурсов, которые замедляют, но не блокируют по IP,
  хватает локальной модификации пакетов (zapret2, byedpi). Это дополнение,
  а не замена: работает до очередного обновления фильтров.
- **Последний рубеж.** Tor с мостами WebTunnel, Psiphon. Медленно, но не
  зависит от ваших серверов.
- **Анонимность.** Утилита её не даёт: хостер видит ваш адрес и способ
  оплаты, у вас один выходной IP на всё.
- **Право.** По состоянию на середину 2026 года использование VPN частным
  лицом в России само по себе не наказуемо, реклама и популяризация средств
  обхода запрещены. Нормы меняются: оцените свой риск сами.

## Что проверено и что нет

Проверено тестами (`go test ./...`):

- ключи X25519 совпадают с эталоном RFC 7748 и закодированы так, как их
  читает Xray; строки VLESS Encryption проходят ту же проверку, что в Xray;
- серверные и клиентские конфиги: состав транспортов, учётные записи,
  маршрутизация, запрет российских адресов на узлах, цепочка relay, пароль и
  порты локального прокси;
- XHTTP не открывает больше трёх соединений;
- автопереключение проверяет только XHTTP и ставит relay последним;
- ссылки и подписка разбираются обратно в те же параметры;
- диагностика различает все вердикты против имитации цензора (заморозка
  ровно на заданном объёме, зависшее рукопожатие, правило всплеска);
- проверочный режим установщика (`--check`) отказывает на подставных хостах
  со старым ядром, без systemd, с занятым портом, без места или инструментов
  и перечисляет все проблемы разом.

Проверено на настоящем Xray v26.11.9 (15.11.2026):

- серверные конфиги выхода и relay и все клиентские приняты `xray run -test`;
- на loopback трафик проходит по XHTTP, Vision и Hysteria2, через relay и
  через `auto.json`;
- установщик выполнен целиком в контейнере Debian без systemd: установка,
  обновление работающего узла, остановка и запуск, удаление;
- Xray и `obhod` запускаются на ядрах 3.2 и 3.16 (Debian 7).

Проверено на настоящем Xray v26.11.9 (16.11.2026):

- локальный прокси отказывает без пароля и с неверным паролем, с паролем из
  `proxy.txt` пропускает трафик по SOCKS5 и HTTP; на порту 10808 никто не
  слушает;
- через конфиг, закреплённый за relay, российский сайт видит адрес клиента,
  а не relay.

Проверено на настоящих серверах (15.11.2026):

- выход на CentOS Stream 10 (systemd 257, SELinux enforcing): установка без
  дополнительных флагов, служба работает, отказов SELinux нет; из зарубежной
  сети трафик проходит по XHTTP, Vision и Hysteria2 и через `auto.json`;
- вход (relay) на Debian 7 с sysvinit и ядром 3.16: установка init-скриптом,
  ссылки автозапуска созданы, Xray работает под непривилегированным
  пользователем; российские направления проходят через него по XHTTP и Vision
  (тогда relay обслуживал их сам, теперь это делает только relay с
  `-allow-ru`);
- `obhod probe` из российской сети дал `IP_BLOCKED` для адреса, который
  действительно недоступен из России, и `CLEAN` для российского входа.

Не проверено:

- связка relay → выход по настоящей сети: адрес первого выхода оказался
  недоступен из России целиком, цепочка проверена только на loopback;
- отказ relay российским назначениям на настоящем сервере: новый конфиг
  принят `xray run -test`, узел с ним не переустанавливался;
- перезагрузка сервера: поднимается ли узел сам, не проверялось ни на
  systemd, ни на sysvinit;
- флаги установщика `--open-firewall` и `--tune-network`; `--install-deps`
  запускался только в контейнере Debian;
- транспорты не испытаны против настоящего ТСПУ: клиент был в зарубежной сети;
- импорт ссылок в мобильные приложения.

Проверка после установки:

```sh
xray run -test -c out/clients/me/xray/nl1-xhttp.json     # конфиг принят
xray run -c out/clients/me/xray/nl1-xhttp.json &
curl -x "$(head -1 out/clients/me/proxy.txt)" https://api.ipify.org   # должен вернуть адрес nl1
```

Повторите для `nl1-vision.json` и `nl1-hy2.json`.
