# План развития obhod

Что уже есть, описано в [README.md](README.md). Здесь то, что решено строить
дальше. Адреса серверов, имена доменов и бакетов в репозиторий не попадают.

**Текущее состояние: этап 0 пройден частично (16.11.2026).** Настоящий Xray
принимает все конфиги; выход и вход установлены на настоящих серверах и по
отдельности пропускают трафик. Не проверены связка вход → выход по настоящей
сети (адрес первого выхода недоступен из России, порты второго закрыты
firewall его хоста) и поведение против ТСПУ:
`obhod probe` снят только с российского хоста и из зарубежной сети. Подробности
в README, раздел «Что проверено и что нет».

## Что решено

| Вопрос | Решение |
|---|---|
| Кто перебирает варианты | Хаб. Клиент исполняет опыты и измеряет; решает сервер. |
| Где хаб | На выходном узле в Германии, реплика на втором. Не в России. |
| Платформы клиента | Компьютер и Android. Android базовый: тонкая оболочка над общим Go-ядром. iOS нет. |
| Служебные каналы | Туннель, бакет в российском объектном хранилище, TXT-записи в DNS для каждого устройства. |
| Отчёты через DNS | Отложены: нужен свой DNS-сервер. Вернуться, если замеры покажут сети, где бакет недоступен, а DNS работает. |
| DNS-зона | Существующая зона занята другим сервисом. Нужен отдельный домен или делегированный поддомен; выбрать до этапа 3. |
| Масштаб | Десятки устройств, хранение в файлах. |
| Смена IP | Только вручную: это деньги. |

## Роли

- **Хаб** знает всё: пользователей, узлы, ключи. Раздаёт конфиги узлам и
  манифесты клиентам, принимает отчёты, ведёт подбор.
- **Агент** на каждом узле применяет конфиг от хаба с проверкой и откатом,
  меряет каналы до соседних узлов, отдаёт статистику.
- **Клиент** на устройстве исполняет планы хаба, держит активный путь и тёплый
  запасной.
- **Утилита администратора** — нынешний `obhod`.

**Путь** — тройка «вход, транспорт, выход». Входы в России, выходы в Германии;
клиент может идти на выход напрямую или через вход.

## Принципы

1. **Российские узлы недоверенные.** На них только их ключи и учётные данные
   для связи с выходами; состояния системы там нет.
2. **Вход не видит назначений.** Клиент шифрует трафик до выхода (VLESS
   Encryption внутри туннеля до входа).
3. **На адресах узлов нет ничего, кроме туннеля.** Служебный канал дублируется
   на инфраструктуре, которая не разделяет судьбу узлов.
4. **Туннели работают без хаба.** При его падении узлы и клиенты живут на
   последнем конфиге.
5. **Правила цензора зашиты в клиент как жёсткие пределы.** План хаба их
   превысить не может.

## Цепочки

- **Выбор выхода клиентом:** байты 7–8 UUID (`vlessRoute` в Xray). `0` — вход
  выбирает сам, `1`, `2` — конкретный выход.
- **Выбор выхода входом:** балансировщик по собственным замерам канала.
- **Канал вход→выход:** два долгоживущих XHTTP-соединения на всех
  пользователей, запасной транспорт Hysteria2. Клиентские сессии идут внутри.
- **Учётные данные различаются по узлам:** выводятся из секрета устройства.
  Изъятый вход не даёт доступа к выходам.

## Протокол управления

Один формат сообщений, три носителя.

| Носитель | Направления | Задержка | Когда |
|---|---|---|---|
| Туннель | оба | мгновенно | жив хоть один путь |
| Бакет | оба | секунды | туннели не строятся |
| DNS (TXT) | к клиенту | от минуты | нет ни туннеля, ни бакета; первый запуск |

Сообщения зашифрованы и подписаны между устройством и хабом. Имена объектов и
записей выводятся из секрета устройства.

Подбор:

1. Клиент сообщает версию ядра, результаты эталонных проверок, последний
   рабочий путь.
2. Хаб отвечает планом: упорядоченный список опытов с пределами по времени и
   объёму.
3. Клиент выполняет шаг и отправляет результат.
4. Хаб выдаёт следующий шаг либо решение: активный путь, запасной, срок.

По ходу подбора хаб может менять серверную сторону: включить транспорт или
порт на лету (`xray api adi`), сменить имя сервера из проверенного набора,
режим XHTTP, пару вход–выход.

Если недоступен ни один носитель, клиент идёт по последнему подписанному
плану из кэша. Через DNS диалога нет: хаб публикует лучшее предположение по
отчётам других устройств той же сети.

**Бакет:** обращение по пути, а не по поддомену (имя бакета не попадает в
SNI); у клиентов только подписанные ссылки с ограниченным сроком; объекты
живут сутки; метка активности хаба лежит там же и служит для переключения на
реплику. Адрес бакета клиент узнаёт из DNS, поэтому бакет заменяем.

## Диагностика

Примитивы в коде, набор проверок и правила вердиктов в конфиге от хаба.

| Примитив | Что выявляет |
|---|---|
| `control` | Есть ли интернет, включены ли белые списки (эталонные сайты). |
| `dns` | Подмена ответов. |
| `tcp` | Чёрный список IP, закрытый порт. |
| `tls` | Фильтр по SNI. |
| `volume` | Заморозка по объёму и её порог. |
| `burst` | Правило всплеска. |
| `udp` | Блокировка UDP; редко и только по правилу. |
| `tunnel` | Блокировка по отпечатку и поведению: реальный профиль через Xray. |
| `chain` | Какое звено цепочки сломано. |
| `mtu`, `clock` | Причины, не связанные с цензурой. |

Доставка отчёта: коротким сообщением по туннелю (умещается под порог
заморозки), через бакет, вручную файлом; неотправленное ждёт в очереди.

## Клиент

- Xray встроен как библиотека: один файл, управление путями без перезапуска.
- Липкое переключение с тёплым запасным, без распределения соединений по
  нескольким путям: смена выходного IP посреди сессии ломает сайты.
- Пределы: одно рукопожатие на узел в 20 с, пауза 130 с после заморозки, без
  смены отпечатка в это время, UDP раз в 10 минут на адрес.
- **Android:** `VpnService` отдаёт дескриптор встроенному TUN-входу Xray;
  приложение исключено из VPN, поэтому его проверки видят сеть без туннеля.
  Один экран, привязка вставкой ссылки, установка APK-файлом.

## Сервер

- Пользователи добавляются и отзываются на лету (`xray api adu`/`rmu`).
  Доступ выдаётся на устройство.
- Статистика по пользователям из Xray; квоты и сроки по желанию.
- Готовые мобильные приложения в подборе не участвуют: получают подписку,
  составленную по сессиям других устройств той же сети.

## Этапы

| № | Что | Готово, когда |
|---|---|---|
| 0 | Проверка текущей версии на настоящем Xray | Каждый транспорт каждого узла пропускает трафик; `obhod probe` снят из домашней сети, мобильной и с российских хостов. |
| 1 | Цепочки: несколько выходов у входа, выбор выхода, сквозное шифрование, раздельные учётные данные | Трафик идёт по каждой паре вход–выход; вход не видит назначений. |
| 2 | Хаб, агент, протокол управления, бакет | Пользователь добавляется без перезапуска; плохой конфиг откатывается; сообщение доходит через бакет при выключенных туннелях. |
| 3 | Ядро клиента, версия для компьютера, DNS-указатель | Клиент находит рабочий путь по плану хаба и переключается при отказе узла. |
| 4 | Android-оболочка | То же на телефоне. |
| 5 | Накопление отчётов, автоматические действия на серверах | Подписка для готовых приложений упорядочена по отчётам. |

## Работа с серверами, которые заняты другим

1. Сначала `scripts/recon.sh`: только чтение.
2. Затем `install.sh --check`.
3. Порты выбирать свободные; 443 у чужого сервиса не отбирать.
4. Без `--tune-network`, `--open-firewall`, `--install-deps`, пока владелец
   явно не согласился на каждое.
5. Узел на адресе почтового сервера — отдельное решение владельца: если адрес
   заблокируют как точку обхода, почта станет недоступна из России. До такого
   решения использовать такой хост только как точку измерения (`obhod probe`
   с него), без входящих портов.
