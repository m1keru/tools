# Самостоятельная сеть ansibles: одна программа, координатор на выходе

Дата: 17.11.2026. Статус: черновик на согласование. Заменяет предыдущий
черновик этого файла (`ansibles apply` и публикация в хранилища): владелец
отверг его как «ручной привод везде».

## Зачем

Задача владельца: скрытая динамическая сеть узлов, которая сама
перестраивает маршруты и маскировки при блокировках. Сейчас любое изменение —
это ручные шаги на ноутбуке, по ssh на каждом узле и рассылка файлов людям.
Владелец хочет вносить изменения в одном месте, а остальное сеть делает сама.
Поведение на телефоне и компьютере одинаковое.

## Что получится

Владелец:

```sh
ansibles node add -name de5 -role exit -ssh ec2-user@АДРЕС   # новый VPS встраивается сам
ansibles node rm de2                                          # узел уходит из сети
ansibles user add anna && ansibles user invite anna              # ссылка-приглашение
ansibles status                                               # узлы, маскировки, алерты
ansibles upgrade                                              # новая версия программы на все узлы
```

Сеть сама:

- держит клиентов на рабочих путях: клиент выбирает вход и маскировку, вход
  выбирает выход;
- включает на узле запасную маскировку, когда текущую режут;
- пишет владельцу в Telegram, когда узел заблокирован из России (заменить
  VPS), когда узел упал (чинить у хостера), когда у узла кончились запасные.

Человек: один раз вставляет приглашение, дальше ничего не делает.

## Цели

- Изменение вносится одной командой на ноутбуке и само доходит до всех узлов
  и устройств.
- Блокировка маскировки обходится без участия владельца.
- Блокировка VPS выявляется с российской стороны, подтверждается и приходит
  владельцу алертом, отличным от «узел упал».
- Одна программа: выход, вход, координатор, клиент на компьютере, ядро
  клиента на Android, команды владельца.

## Не цели

- Автоматический заказ VPS через API хостеров: VPS заменяет владелец по
  алерту.
- Раздача разных подмножеств узлов разным людям: все знают всё. Формат списка
  узлов это допускает (поле «кому»), но пока везде «всем».
- Общие знания между клиентами по операторам (в такой-то сети работает такая-то
  маскировка).
- Внешние каналы: бакеты, DNS. Потерявшемуся устройству владелец выдаёт новое
  приглашение.
- iOS, UDP-маскировки (Hysteria2), автообновление самой программы на
  устройствах.
- Разные учётные данные человека на разных узлах (PLAN.md, этап 1): пока у
  человека один UUID на всех узлах.
- Копия координатора на втором выходе с автоматическим переходом (см.
  «Координатор упал»).
- Вход, который сам обслуживает российские сайты для сетей с белыми списками
  (нынешний `-allow-ru`): сейчас ни один узел им не пользуется. Вернуть, если
  такие сети станут реальной проблемой. *(Решение проектировщика.)*

## Анти-цели (провал, даже если работает)

- Программа на сервере трогает чужое: пакеты, ядро, sysctl, чужие сервисы,
  firewall без согласия владельца на этот хост.
- Координатор или любой узел может добавить узел или человека либо включить
  маскировку вне набора, подписанного владельцем.
- Координатор хранит адреса клиентов.
- Российский вход видит содержимое служебного обмена клиентов с координатором.
- Клиент заметен: ходит к координатору синхронно с другими или чаще раза в
  15 минут, переключается чаще раза в 2 минуты (пауза после заморозки).
- На узле одновременно открыто больше двух маскировок.
- Ложный алерт «заблокирован» по одному замеру: владелец снесёт живой узел.
- Адреса, имена серверов, ключи или токены попадают в репозиторий.

## Ограничения

- Правила работы с чужими серверами из PLAN.md остаются: сначала разведка
  (только чтение), затем проверка, порты только свободные, флаги вроде
  открытия firewall — только с согласия владельца для конкретного хоста.
- Хосты бывают с systemd и с sysvinit, архитектуры amd64 и arm64, старые ядра
  (самое старое сейчас 3.16, на нём уже работает Xray).
- У облачных хостов свой firewall в консоли: порты основной и всех запасных
  маскировок владелец открывает там заранее, иначе запасная не включится.
- Журнал обращений выключен везде.
- Без постоянных ssh-сессий: каждый вызов ssh — отдельный процесс.

## Подходы

| Вопрос | Варианты | Выбрано |
|---|---|---|
| Где сеть «думает» | 1) координатор на выходе, одна программа везде; 2) равноправные узлы без координатора; 3) агент рядом с нынешними Xray-службами | **1**. 2 — в разы сложнее сделать правильно, российские входы видели бы отчёты, на 3–10 узлах выигрыша нет. 3 — два процесса на узле, каждое переключение рвёт соединения перезапуском, на Android всё равно нужно встраивание |
| Граница автономии | 1) сеть перестраивается по имеющимся узлам, VPS заменяет владелец; 2) сеть ещё и заказывает VPS | **1**, с алертом о блокировке |
| Что значит «адаптироваться» | А) только выбор пути; Б) плюс смена маскировки; В) плюс общие знания по операторам | **Б**: запасные заранее у клиентов, базовый набор в приглашении |
| Кто что знает | все знают всё; каждому подмножество | **все знают всё**, формат под подмножества |
| Внешний канал | российский бакет; без него | **без него** |
| Готовые приложения (Happ с подпиской) | — | отвергнуты как полумера |

## Как устроено

### Одна программа

`ansibles` — Go-программа со встроенным xray-core. Роли:

| Роль | Где | Что делает |
|---|---|---|
| выход | VPS за границей | принимает клиентов и входы, выпускает в интернет, проверяет соседей |
| вход | VPS в России | принимает клиентов, ведёт трафик на выходы, смотрит на выходы с российской стороны |
| координатор | дополнительно на одном выходе | хранит состояние, принимает отчёты, решает переключения, шлёт алерты |
| клиент | компьютер; ядро для Android | держит человека на рабочем пути, отчитывается |
| команды владельца | ноутбук | подписывает изменения, ставит узлы по ssh, спрашивает состояние |

Конфиг Xray каждая роль собирает сама из состояния сети. Логика нынешнего
генератора (`client.go`, `server.go`: профили, балансировщик, проверки
здоровья, «российское напрямую», отказ узлов российским направлениям)
переезжает в общую библиотеку и работает на узлах и клиентах, а не на
ноутбуке. Входы, пользователи и маскировки меняются в работающем ядре на лету
(в Xray это есть: менеджер входов и менеджер пользователей); перезапуск ядра —
только если иначе нельзя.

### Состояние сети

Три части, у каждой свой круг читателей:

| Часть | Что внутри | Кто подписывает | Кто получает |
|---|---|---|---|
| Карта | версия; узлы: имя, роль, адрес, выходы входа, координатор ли, поле «кому» («всем» или «только узлы»; позже — список людей); маскировки узла: транспорт, порт, сайт-маска, открытые ключи; адрес и открытый ключ координатора | владелец | все: узлы и клиенты |
| Список людей | версия; имя и UUID каждого; отозванные | владелец | только узлы |
| Оперативка | какие маскировки сейчас включены на каждом узле, здоровье узлов | координатор (его ключ записан в карте) | узлы и клиенты |

- Ключ подписи владельца (Ed25519) лежит только на ноутбуке, рядом с
  состоянием, в `.gitignore`.
- Приватные ключи узла (REALITY, шифрование XHTTP) узел создаёт сам при
  установке и никому не отдаёт: в карту уходят только открытые. Ни ноутбук,
  ни координатор не могут выдать себя за узел.
- Версии растут монотонно; более старую версию никто не принимает.
- Клиент проверяет подпись владельца на карте и подпись координатора на
  оперативке. Оперативка не может включить маскировку, которой нет в карте.

### Маскировки

Маскировка — транспорт (XHTTP или Vision, оба поверх REALITY, только TCP),
порт и сайт-маска. При установке узел получает основную и 2–3 запасные:

- сайты-маски берутся из списка по хостерам *(решение владельца)*: файл
  `targets.txt` рядом с состоянием, в `.gitignore`, строка на группу —
  имя группы, окончание обратного DNS-имени адресов этого хостера (если
  есть), затем сайты. Совет README сохраняется: сайт в сети того же
  хостера, для входов — российские сайты. Список ведёт владелец, редко;
- группу `node add` выбирает по флагу `-hoster` или по окончанию обратного
  DNS-имени адреса узла; не нашёл — останавливается и просит `-hoster` или
  `-targets` (флаг `-targets` перекрывает список);
- каждый сайт проверяется с самого сервера одним обычным TLS-соединением,
  критерий тот же, что сейчас в `targetProblem`: TLS 1.3, обмен ключами
  X25519, HTTP/2. Сканирования соседей нет;
- у одного узла сайты разные; между узлами предпочитаются ещё не занятые;
- порты — только свободные на этом хосте, проверяются при установке;
- все запасные сразу попадают в карту, поэтому клиенты знают их заранее.

Одновременно на узле включено не больше двух маскировок. Запасная
**добавляется** к работающей; старая выключается, когда ею несколько часов
никто не пользовался.

**SSH у входов — последняя запасная** *(решение владельца)*. Кроме маскировок
на Xray, у каждого входа в карте есть маскировка «SSH на свободном порту».
Координатор включает её, только когда у входа не проходит ни одна маскировка
на Xray, и она считается в «не больше двух». Клиент пробует её последней.

- Сервер тот же, что на выходах для связи вход–выход (раздел ниже). Клиент
  открывает потоки к локальному SOCKS-входу Xray на входе, дальше трафик
  идёт как обычно.
- Ключ SSH человека клиент выводит из своего UUID (Ed25519 из
  HMAC-SHA256(UUID, "ansibles ssh")); открытые ключи входы берут из списка
  людей. Это та же степень доверия, что и сам UUID: у входа он уже есть.
  Приглашение не меняется.
- Только TCP: звонки в мессенджерах по UDP на этом пути не работают или
  работают хуже; сайты, сообщения, видео проходят.
- От блокировки адреса входа не спасает; помогает, если режут Xray по
  признакам протокола.

### Связь вход–выход

У каждой пары «вход–выход» своя маскировка *(решение владельца)*:

| | Что | Когда |
|---|---|---|
| Основная | Xray: VLESS поверх XHTTP и REALITY, как сейчас; вход ходит на включённую маскировку выхода под своей учётной записью | всегда, пока проходит |
| Запасная | SSH | координатор переводит пару на SSH, когда вход сообщает, что XHTTP до выхода не проходит или замерзает, а из-за границы выход жив |

SSH устроен так:

- SSH-сервер встроен в программу на выходе и слушает **свободный порт**
  этого хоста. sshd самого хоста (порт 22) не трогается, пользователей на
  хостах не заводим.
- Пускает только входы: ключ SSH вход создаёт сам при установке, открытая
  часть — в карте. Порт открыт всегда; на выходе с согласием «только входы»
  firewall пускает к нему только адреса входов. Этот порт не считается в
  «не больше двух маскировок» (он только для узлов) и печатается в списке
  портов для облачной консоли.
- Сервер представляется так же, как обычный OpenSSH на Linux, а не строкой
  по умолчанию библиотеки Go, которая сразу выдаёт необычный сервер.
- Вход держит одно SSH-соединение к выходу и пускает по нему потоки
  (каналы `direct-tcpip`) к локальному SOCKS-входу Xray на выходе. Поэтому
  правила выхода (отказ российским направлениям, порт 25, торренты)
  действуют и для трафика через SSH. Xray на входе ходит в этот туннель
  через локальный SOCKS-выход.
- Только TCP: UDP клиентов через вход на SSH не идёт (браузеры уходят с QUIC
  на TCP сами).
- Назад на XHTTP координатор специально не переключает: пара остаётся на SSH,
  пока SSH работает; начал сбоить — пробуется XHTTP.
- Библиотека SSH — `golang.org/x/crypto/ssh` от авторов Go.

Основание: замер 16.11.2026 — SSH из двух российских сетей за границу несёт
30 МБ на 2–4 МБ/с без остановок; Xray через вход — 2,8 МБ/с.

### Связь с координатором

Внутри тех же туннелей, отдельных каналов нет.

- Координатор отвечает на зарезервированном имени (`coord.ansibles.invalid`:
  домен `.invalid` никогда не существует снаружи).
- На каждом узле правило маршрутизации ведёт это имя к координатору: на самом
  координаторе — на его локальный порт (прямой выход Xray с разрешением ровно
  этого адреса через `finalRules`), на выходе — через туннель к выходу с
  координатором, на входе — через свои выходы.
- Внутри — HTTPS с открытым ключом координатора из карты. Российский вход
  пересылает служебный обмен, но прочитать его не может.
- Клиент ходит к координатору через своё же ядро (`core.Dial`), то есть тем же
  путём, что и его трафик.

Кто как часто:

| Кто | Что | Когда |
|---|---|---|
| клиент | забрать карту и оперативку, если версия новее; отдать отчёт | при запуске, затем раз в 15 минут ±3 минуты |
| узел | забрать карту, список людей, оперативку; отдать замеры | раз в минуту |
| ноутбук | отдать новую подписанную карту или список людей | по команде владельца |

### Отчёты, переключения и алерты

**Клиент сообщает** по каждой маскировке каждого узла, которую пробовал:
сколько попыток прошло, сколько нет и как именно не прошло (отказ, сброс,
таймаут, заморозка на N килобайтах; классификация та же, что в
`ansibles legacy probe`). Отчёт едет вместе с очередным обращением за картой, лишних
обращений нет. Адрес клиента координатор не хранит.

**Узлы сообщают:** выходы и координатор раз в минуту проверяют включённые
маскировки всех узлов из-за границы. Входы проверяют выходы с российской
стороны.

**Правила координатора** *(пороги — предложение проектировщика)*:

| Что видно | Что делает координатор |
|---|---|
| Маскировка не проходит у двух и более людей 15 минут, узел жив из-за границы, другие его маскировки у кого-то проходят | включает запасную (если включено меньше двух) |
| Все маскировки узла не проходят с двух и более российских точек (люди или входы) 15 минут, из-за границы узел жив | алерт «заблокирован из России, замените VPS» |
| Узел недоступен и из-за границы 5 минут | алерт «узел упал» |
| Запасные маскировки узла кончились | алерт «у узла кончились запасные» |

Один алерт на каждое изменение, напоминание раз в сутки, пока не исправлено.
Алерты идут через Telegram-бота: бота заводит владелец, токен и номер чата
`ansibles` кладёт по ssh на каждый выход при установке (на входы — никогда).

### Координатор упал

Трафик идёт дальше по последнему состоянию: узлы и клиенты живут без
координатора. Перестают работать переключения и алерты. Поэтому каждый
выход, который 10 минут не может связаться с координатором, сам шлёт
владельцу алерт «координатор недоступен»: токен бота лежит на каждом выходе
(все выходы за границей и одинаково доверенные, координатор и так живёт на
одном из них), на входы он не попадает. *(Решение проектировщика.)* Перенос
роли — одна команда `ansibles coordinator move ИМЯ`:
подписанные части лежат на ноутбуке, оперативку координатор набирает заново
за несколько минут. Копия с автоматическим переходом — потом, если
понадобится.

### Добавление и удаление узла

`ansibles node add -name N -role exit|entry -ssh user@host [флаги согласия]`:

1. По ssh: разведка (только чтение) и проверка хоста: архитектура, система
   инициализации, свободные порты, место. Неожиданное — стоп.
2. Копирует программу нужной архитектуры с ноутбука (GitHub не нужен).
3. `ansibles node init` на сервере: создаёт ключи и маскировки, возвращает
   открытую часть.
4. На ноутбуке: новая версия карты, подписанная владельцем; отправка
   координатору.
5. Ставит службу (systemd или sysvinit) и запускает. Узел забирает список
   людей и оперативку у координатора и начинает работать.
6. Печатает порты основной и запасных маскировок, которые надо открыть в
   облачной консоли, и проверяет с ноутбука, открыты ли они.

Вход по умолчанию ходит на все выходы карты, поэтому новый выход
подхватывается входами сам. Выход, который должен пускать только входы
(сейчас так у одного узла), ставится с согласием владельца на управление
firewall; список разрешённых адресов узел обновляет сам при смене входов в
карте. В карте у такого выхода «кому: только узлы»: клиентам он не выдаётся,
потому что достучаться до него они всё равно не могут, а его адрес в каждом
телефоне — только риск. «Все знают всё» относится к узлам, открытым для
клиентов. *(Решение проектировщика.)*

Флаги согласия: `-open-firewall`, `-entries-only` (выход пускает только
входы), `-install-deps`. Без них программа firewall и пакеты не трогает.

`ansibles node rm N`: карта без узла, подписанная владельцем; клиенты и входы
перестают на него ходить. Сам VPS владелец удаляет у хостера.

### Обновление программы на узлах

Xray встроен в программу, поэтому новый выпуск Xray — новая версия `ansibles`.
Обновляет владелец, когда сам решил, одной командой `ansibles upgrade` с
ноутбука по ssh *(решение владельца)*:

1. По одному узлу: выходы, затем входы; координатор последним.
2. Копирует программу нужной архитектуры, предыдущую оставляет рядом.
3. Перезапускает службу и ждёт, что узел поднялся и координатор видит его
   здоровым (для координатора — что он сам отвечает).
4. Не дождался за 2 минуты — возвращает предыдущую версию, перезапускает и
   останавливает весь `upgrade`, называя узел.

Отвергнуто: узлы сами забирают подписанную версию у координатора — крупный
компонент ради редкого события, а плохая сборка без отката кладёт все узлы
разом.

### Люди и приглашения

- `ansibles user add ИМЯ` / `user rm ИМЯ`: новый список людей, узлы принимают или
  отвергают человека на лету.
- `ansibles user invite ИМЯ`: ссылка `ansibles://join/…`: UUID человека, открытый
  ключ владельца, адрес и ключ координатора и базовый набор — 2–3 входа по
  2–3 маскировки, которые по оперативке сейчас проходят. Передаётся так же,
  как сейчас папка: не через российские мессенджеры и почту.
- Ключ — на человека; несколько устройств одного человека используют одно
  приглашение.

### Клиент

- Хранит в каталоге настроек пользователя (права 0600): приглашение, карту,
  оперативку.
- Собирает конфиг Xray из карты: все узлы, все маскировки, включённые по
  оперативке впереди; балансировщик и проверки здоровья — как сейчас в
  `auto.json`; российское напрямую.
- Не переключается чаще раза в 2 минуты.
- SSH-маскировку входа пробует последней, когда маскировки на Xray у всех
  известных путей не проходят; SSH-клиент встроен в то же ядро.
- Если все известные пути не работают дольше часа, говорит человеку прямо:
  «все известные узлы недоступны, попросите новое приглашение».
- Компьютер (macOS, Windows, Linux): `ansibles client join 'ansibles://join/…'`,
  затем `ansibles client run` в терминале. Локальный прокси с паролем, как
  сейчас; адрес и пароль печатаются при запуске. Автозапуск — не в этой
  работе.
- Android: оболочка на Kotlin в `ansibles/android/`, ядро — тот же код через
  `gomobile bind`. `VpnService` отдаёт дескриптор, ядро передаёт его
  встроенному TUN-входу Xray (переменная `xray.tun.fd`). Один экран:
  состояние, кнопка, вставка приглашения, выбор приложений для туннеля
  (остальные идут мимо, само приложение тоже). Foreground-сервис с
  уведомлением. APK подписывается ключом владельца с ноутбука, ставится
  файлом.
- Нужны урезанные `geoip.dat` и `geosite.dat` (правила `geoip:ru`,
  `geoip:private`, `geosite:category-ru`).

## Переход с нынешней системы

1. Новая программа проверяется в лаборатории: несколько узлов на одной
   машине и песочница владельца (отдельная виртуалка arm64 для экспериментов)
   как настоящий выход.
2. Нынешние узлы переводятся по одному командой `node add` поверх старой
   установки: служба Xray от `install.sh` удаляется своим `--uninstall`,
   ключи создаются заново.
3. Люди получают приглашения. Старые `auto.json` перестают работать по мере
   перевода узлов; переводить, когда приглашения уже у людей.
4. После перевода из репозитория уходят `install.sh.tmpl`, `render`, рассылка
   файлов; README, CLIENTS.md, PLAN.md переписываются.

## Этапы

| № | Что | Готово, когда |
|---|---|---|
| 1 | Программа в ролях выход и вход, координатор, `node add/rm`, `user add/rm`, `status`, `upgrade`, алерт «узел упал» | в лаборатории и на песочнице узлы встают одной командой, новая карта доходит до узлов сама, выключенный узел даёт алерт |
| 2 | Клиент для компьютера, приглашения | на ноутбуке клиент по приглашению выходит в интернет; после `node add` нового выхода клиент сам начинает его использовать |
| 3 | Перевод нынешних узлов и людей | все узлы на новой программе, люди на приглашениях, старый генератор удалён |
| 4 | Отчёты, запасные маскировки, SSH: запасная связь вход–выход и последняя запасная маскировка входов, алерт «заблокирован» | в лаборатории искусственная заморозка маскировки ведёт к включению запасной, клиент уходит на неё сам; заморозка XHTTP между входом и выходом переводит пару на SSH, трафик клиентов идёт дальше; при заморозке всех Xray-маскировок входа клиент выходит через SSH на вход; полная «блокировка» узла даёт алерт, одиночный сбой — нет |
| 5 | Android | на телефоне владельца: приглашение, туннель для выбранных приложений, переключения |

## Проверка

- Подписи: чужая подпись, старая версия, маскировка вне карты — отвергаются.
- Правила координатора: на подставных отчётах — включение запасной, алерты,
  отсутствие алерта от одного источника и от короткого сбоя.
- Сборка конфигов из карты: те же проверки, что сейчас у генератора
  (`config_test.go`), переносятся.
- Лаборатория на одной машине: выход, вход, координатор, клиент; блокировка
  имитируется отказом порта и обрывом после N килобайт.
- Песочница: настоящий выход на arm64 с systemd.
- Настоящие узлы при переводе: разведка и проверка перед каждым.
- Телефон владельца на этапе 5.

## Оставлено строителю

- Менять конфиг в работающем ядре или перезапускать ядро при каждом изменении
  (критерий: соединения не рвутся при включении запасной маскировки).
- Форма HTTP-обмена с координатором и формат хранения его состояния.
- Как собирать урезанные geoip и geosite.
- Минимальная версия Android и разметка экрана.
- Точные пороги после лаборатории (15 минут, две точки, «несколько часов»).
